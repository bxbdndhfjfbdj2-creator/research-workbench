# 世界语言 0.1 设计规格

## 一、目的

世界语言 0.1 的目标不是继续增加请假审批、表单、流程节点等 OA 功能，而是验证一个更底层的问题：

> 能否用一小组中文形式语句定义一个世界，并让事件依据规律自动改变这个世界，同时把每一步推导过程解释给人看。

当前“星河公司”演示只是第一个示例世界。解释器本身不得写死“员工、经理、请假、直属负责人、审批”等组织概念。

成功标准：

1. 页面中的组织、成员、关系、状态和规律全部来自用户可编辑的世界语言源码，而不是写死在 JavaScript 中。
2. 用户输入一个事件后，解释器能够匹配规律、绑定未知存在、读取现有事实，并产生新的存在、关系或状态。
3. 页面必须展示“为什么得到这个结果”，包括命中的规律、变量绑定、使用的事实和产生的变化。
4. 同一个解释器无需修改代码即可运行另一个简单领域示例，例如学校或工厂。
5. 第一版保持确定性、可解释和可测试，不加入自然语言模型、数据库、登录、概率、主体认知或可能世界。

## 二、设计原则

### 1. 语言优先

世界模型由源码定义，界面只是源码与运行状态的可视化。不能让界面按钮成为真正的业务逻辑来源。

### 2. 世界优先，而不是流程优先

语言描述“什么存在、它们之间有什么关系、当前是什么状态、发生了什么、什么规律会产生什么变化”。流程只是这些事实和规律在特定领域中的结果。

### 3. 领域概念不是解释器原语

以下概念都不得写进解释器核心：员工、经理、学生、教师、请假、审批、任务、工厂、机器、所有权。

它们必须通过语言源码定义或作为普通符号出现。

### 4. 结果必须可解释

每次规律执行都要留下推导记录，至少回答：

- 哪个事件触发了哪条规律；
- 每个未知存在被绑定成了什么；
- 哪些已有事实使条件成立；
- 最终新建或修改了什么。

### 5. 先小后大

0.1 只解决确定性的单世界运行。时间、概率、观察、认知、反事实和多主体推演留给后续版本。

## 三、语言核心

0.1 只有六类顶层概念：

- 世界
- 存在
- 关系
- 状态
- 规律
- 事件

“任务”不是核心概念。组织领域中的任务通过“新建一个任务类型的存在 + 设置关系 + 设置状态”表达。

## 四、基本语法

### 1. 世界

```text
世界 星河公司
```

每个程序必须且只能有一个世界声明。

### 2. 存在

```text
存在 张三 是 员工
存在 李四 是 经理
```

语义：声明一个命名存在，并赋予一个类型。

同一个存在可以拥有多个类型声明；完全重复的声明视为幂等，不产生第二个存在。

### 3. 关系

```text
关系 张三 的 直属负责人 是 李四
```

语义：建立一个有方向的三元事实：

```text
主体 --关系名--> 客体
```

关系默认允许一对多。0.1 不做基数约束。

### 4. 状态

```text
状态 张三 的 出勤状态 是 在岗
状态 李四 的 出勤状态 是 在岗
```

语义：某个存在在一个命名状态槽位上只有一个当前值。

例如“张三 / 出勤状态”在任何时刻只有一个当前值。设置新值会替换旧值，但运行记录中保留变化过程。

### 5. 事件

```text
事件 张三 申请 请假
```

事件由若干有序符号组成。0.1 不尝试理解自然语言，只进行严格的符号匹配。

例如：

```text
事件 李四 批准 请假审批任务一
```

也是合法事件。

### 6. 规律

示例：

```text
规律 请假审批

    当 事件 ?员工 申请 请假

    且 存在 ?员工 是 员工
    且 关系 ?员工 的 直属负责人 是 ?负责人

    则 新建 ?任务 是 请假审批任务
    并 设置关系 ?任务 的 申请人 为 ?员工
    并 设置关系 ?任务 的 负责人 为 ?负责人
    并 设置状态 ?任务 的 处理状态 为 待处理
```

规律由三部分组成：触发、条件、效果。

## 五、未知存在与绑定

以 `?` 开头的名称表示规律中的未知存在，例如：

```text
?员工
?负责人
?任务
```

这不是面向用户暴露的“传统变量系统”，而是规律匹配中的占位符。

### 绑定规则

1. `当 事件 ...` 首先依据实际事件绑定其中出现的未知存在。
2. 后续每条 `且` 条件在当前绑定基础上查找世界事实。
3. 一条条件可以绑定新的未知存在，例如：

```text
关系 ?员工 的 直属负责人 是 ?负责人
```

在 `?员工 = 张三` 已知时，可以通过世界中的关系事实绑定 `?负责人 = 李四`。
4. 如果一组条件产生多组完整绑定，规律对每组绑定分别执行一次。
5. 同一个事件实例、同一条规律、同一组绑定最多执行一次，避免重复产出。
6. 效果中引用的未知存在必须已经绑定，或者由该规律中的 `新建` 语句创建。

## 六、效果语句

0.1 支持四种效果。

### 1. 新建存在

```text
新建 ?任务 是 请假审批任务
```

运行时生成一个新的存在，并把它绑定到 `?任务`。

生成的内部标识必须唯一；界面同时生成可读名称，例如：

```text
请假审批任务一
请假审批任务二
```

### 2. 设置关系

```text
设置关系 ?任务 的 负责人 为 ?负责人
```

加入一条关系事实。

完全重复的关系设置视为幂等。

### 3. 设置状态

```text
设置状态 ?员工 的 出勤状态 为 请假已批准
```

替换该存在对应状态槽位的当前值。

### 4. 不支持的效果

0.1 暂不支持删除存在、删除关系、算术运算、循环、函数调用、网络调用和外部副作用。

## 七、默认示例程序

默认页面加载以下语义等价的“星河公司”程序。

```text
世界 星河公司

存在 张三 是 员工
存在 李四 是 经理

关系 张三 的 直属负责人 是 李四

状态 张三 的 出勤状态 是 在岗
状态 李四 的 出勤状态 是 在岗

规律 请假审批

    当 事件 ?员工 申请 请假

    且 存在 ?员工 是 员工
    且 关系 ?员工 的 直属负责人 是 ?负责人

    则 新建 ?任务 是 请假审批任务
    并 设置关系 ?任务 的 申请人 为 ?员工
    并 设置关系 ?任务 的 负责人 为 ?负责人
    并 设置状态 ?任务 的 处理状态 为 待处理

规律 请假批准

    当 事件 ?负责人 批准 ?任务

    且 存在 ?任务 是 请假审批任务
    且 关系 ?任务 的 负责人 是 ?负责人
    且 关系 ?任务 的 申请人 是 ?员工
    且 状态 ?任务 的 处理状态 是 待处理

    则 设置状态 ?任务 的 处理状态 为 已完成
    并 设置状态 ?员工 的 出勤状态 为 请假已批准

规律 请假驳回

    当 事件 ?负责人 驳回 ?任务

    且 存在 ?任务 是 请假审批任务
    且 关系 ?任务 的 负责人 是 ?负责人
    且 关系 ?任务 的 申请人 是 ?员工
    且 状态 ?任务 的 处理状态 是 待处理

    则 设置状态 ?任务 的 处理状态 为 已完成
    并 设置状态 ?员工 的 出勤状态 为 请假已驳回
```

这个示例必须由通用解释器执行，解释器内部不得出现“张三”“李四”“请假审批”等特殊判断。

## 八、运行语义

### 1. 建立世界

点击“建立世界”后：

1. 解析源码；
2. 检查语法；
3. 检查引用与规律完整性；
4. 建立初始存在、关系、状态和规律；
5. 清空之前的运行事件与推导记录；
6. 渲染当前世界。

如果源码有错误，不替换当前可运行世界，而是在编辑器附近显示错误。

### 2. 输入事件

用户输入：

```text
张三 申请 请假
```

页面把它规范化为一个事件实例，并依次测试所有规律。

### 3. 规律匹配

对每条规律：

1. 匹配 `当 事件` 模式；
2. 形成初始绑定；
3. 逐条求值 `且` 条件；
4. 获得零组、一组或多组完整绑定；
5. 对每组绑定执行效果；
6. 记录推导轨迹。

0.1 中规律按照源码顺序求值。一个外部事件处理完成后才接受下一个外部事件。

### 4. 状态更新

所有效果立即应用到当前世界。

同一个规律执行中的效果按照源码顺序执行，因此后面的效果可以引用前面 `新建` 出来的存在。

### 5. 不做自动事件级联

0.1 中规律效果不会自动产生新的语义事件。规律产生的变化会记录在推导轨迹中，但不会再次触发其他规律。

自动产生事件与级联规则留到后续版本，避免 0.1 引入循环和终止性问题。

## 九、解析与语义错误

### 1. 解析错误

必须显示：

- 行号；
- 出错行；
- 期望的语句形式；
- 简短中文原因。

例如：

```text
第 8 行：无法识别“张三 属于 研发部”
期望：关系 <主体> 的 <关系名> 是 <客体>
```

### 2. 语义错误

建立世界时至少检查：

- 缺少世界声明；
- 多个世界声明；
- 重名规律；
- 初始状态对同一“存在 + 状态槽位”给出冲突值；
- 规律效果引用既未绑定也未新建的未知存在；
- `新建` 重复声明同一个未知存在；
- 不完整的规律结构，例如有 `则` 但没有 `当`。

### 3. 事件运行错误

事件没有命中任何规律不是错误。界面显示：

```text
事件已记录，但没有规律被触发。
```

## 十、内部世界模型

实现层建议把世界存成以下逻辑结构：

```text
世界
├── 名称
├── 存在集合
│   └── 每个存在：内部标识、显示名称、类型集合
├── 关系集合
│   └── 主体、关系名、客体
├── 状态表
│   └── 主体 + 状态槽位 -> 当前值
├── 规律集合
├── 事件历史
└── 推导历史
```

解释器只操作这套结构，不直接操作页面元素。

## 十一、组件边界

### 1. 解析器

建议文件：`src/parser.js`

职责：

- 把中文源码转成结构化语法树；
- 保存源码行号；
- 只负责语法，不执行规律。

### 2. 验证器

建议文件：`src/validator.js`

职责：

- 检查世界级语义错误；
- 检查规律中的未知存在作用域；
- 输出带行号的中文错误。

### 3. 世界运行时

建议文件：`src/runtime.js`

职责：

- 从已验证的语法树建立世界；
- 接收事件；
- 匹配规律；
- 求解绑定；
- 执行效果；
- 生成推导轨迹。

运行时不得依赖 DOM。

### 4. 默认程序

建议文件：`src/default-program.js`

职责：仅保存默认示例源码，不包含业务执行代码。

### 5. 页面控制器

继续使用：`src/app.js`

职责：

- 读取编辑器文本；
- 调用解析器、验证器和运行时；
- 把世界状态、事件历史和推导轨迹渲染出来；
- 不实现领域规则。

原有 `src/engine.js` 的请假专用逻辑在新运行时稳定后删除。

## 十二、页面设计

页面调整为四个主要区域。

### 1. 世界语言编辑器

显示可编辑源码和“建立世界”按钮。

默认加载星河公司示例。

### 2. 当前世界

通用展示：

- 所有存在及其类型；
- 所有关系；
- 所有当前状态；
- 所有规律名称。

页面不得通过“员工卡片”“经理卡片”之类的硬编码假设世界一定是公司。

### 3. 事件输入

单行输入框，例如：

```text
张三 申请 请假
```

建立世界后才能发生事件。

对于默认示例，可提供快捷事件按钮，但按钮只是填入事件文本并调用同一个通用事件接口，不得直接调用请假专用函数。

### 4. 推导结果

每次事件后显示一张推导卡片，例如：

```text
事件：张三 申请 请假

命中规律：请假审批

绑定：
?员工 = 张三
?负责人 = 李四
?任务 = 请假审批任务一（新建）

使用事实：
存在 张三 是 员工
关系 张三 的 直属负责人 是 李四

产生变化：
新建 请假审批任务一 是 请假审批任务
关系 请假审批任务一 的 申请人 是 张三
关系 请假审批任务一 的 负责人 是 李四
状态 请假审批任务一 的 处理状态 是 待处理
```

这是 0.1 的关键产品体验。

## 十三、测试策略

实现必须先写测试再写运行代码。

至少覆盖：

### 解析器

1. 能解析一个最小世界；
2. 能解析存在、关系、状态；
3. 能解析带多个条件和多个效果的规律；
4. 错误语句返回正确行号；
5. 空行和缩进不改变语义。

### 验证器

1. 缺少世界声明失败；
2. 重名规律失败；
3. 未绑定未知存在失败；
4. 冲突初始状态失败。

### 运行时

1. `张三 申请 请假` 能绑定 `?员工 = 张三`；
2. 能通过关系继续绑定 `?负责人 = 李四`；
3. 能新建请假审批任务存在；
4. 新任务拥有申请人、负责人和待处理状态；
5. `李四 批准 <任务>` 能完成任务并修改张三状态；
6. `李四 驳回 <任务>` 能产生对应状态；
7. 错误负责人无法命中批准规律；
8. 没有匹配规律的事件不会修改世界；
9. 同一事件实例不会对同一绑定重复执行同一规律。

### 领域无关性

至少增加一个非组织审批示例测试，例如：

```text
世界 第一中学
存在 王小明 是 学生
存在 李老师 是 教师
关系 王小明 的 班主任 是 李老师
```

用通用规律证明解析器与运行时没有依赖“公司、员工、请假”等特殊词。

## 十四、部署约束

继续保持纯前端、无数据库架构。

当前公网演示通过 Railway 服务读取 `organization-language-demo` 分支上的静态文件。新版本完成后沿用同一公开地址，不创建新的用户数据存储。

页面刷新后恢复默认程序和初始世界，符合 0.1 的演示定位。

## 十五、明确不做的内容

0.1 不实现：

- 任意自然语言理解；
- 大语言模型自动生成规律；
- 时间推进与持续过程；
- 概率与不确定性；
- 主体的观察、相信和知识；
- 可能世界和反事实；
- 自动事件级联；
- 数值计算和表达式系统；
- 权限、安全和多人协作；
- 数据库和外部系统连接；
- 领域专用表单设计器；
- 图形化流程设计器。

这些能力只有在 0.1 证明“中文源码可以可靠定义并驱动一个小世界”后才进入下一阶段。

## 十六、验收场景

最终演示必须完成以下流程：

1. 用户看到默认星河公司源码；
2. 点击“建立世界”；
3. 页面显示张三、李四、直属负责人关系和出勤状态；
4. 输入“张三 申请 请假”；
5. 页面显示命中“请假审批”规律；
6. 页面明确显示 `?员工 = 张三`、`?负责人 = 李四`；
7. 世界中出现一个新建的请假审批任务存在，并显示其关系和状态；
8. 输入“李四 批准 <该任务名称>”；
9. 任务状态变成已完成，张三出勤状态变成请假已批准；
10. 修改源码，把“张三的直属负责人”从李四改成王五并增加王五存在后，重新建立世界；
11. 再次输入“张三 申请 请假”，新任务负责人自动变成王五，而不修改任何 JavaScript 业务逻辑；
12. 替换为简单学校示例后，解释器仍能正常建立和运行世界。

只要第 10 至第 12 步成立，就证明这个版本已经从“写死的 OA 演示”跨到了“通用世界语言运行时”。
