# Research Workbench 第一版设计规格

- 状态：已批准
- 日期：2026-09-29
- 适用对象：固定 6 人、单一团队、私有部署、不开放公众注册的社会科学研究团队
- 运行模式：AI 原生、混合型智能代理协作
- 核心依赖：DeepSeek Harness（独立运行时）、GitHub（工程事实源）

## 1. 设计目标

Research Workbench 是一个面向小型社会科学研究团队的 AI 原生科研协同工作台。第一版针对 6 人团队：1 名总负责人负责研究组合、关键科学节点和资源协调；5 名研究成员各自主导 1 项研究，同时以交叉协作者、方法挑战者或理论/复现挑战者身份参与其他项目。

系统的目标不是把科研压缩成线性流程，也不是做一个带 AI 聊天框的任务管理器，而是建立一个能够表达真实科研探索过程的工作环境：研究可以回退、分叉、并行、重新开启；数据、代码、文献、方法、模型、指标、文档和智能代理技能可以跨项目沉淀与复用；AI 可以执行大量工程性和分析性工作，但不能静默改变研究的正式科学含义。

系统的核心目标是：

1. 把研究者的注意力从机械执行转移到科学判断。
2. 让研究过程可追踪、可解释、可复现、可审计。
3. 让科研结果、失败经验和工具资产跨项目累积。
4. 让 AI 智能代理成为受控执行主体，而不是不可审计的聊天助手。
5. 让总负责人通过研究组合视角管理关键不确定性、科学风险和资源冲突，而不是逐项追踪普通任务。

## 2. 第一版边界

### 2.1 第一版必须支持

- 固定 6 名团队成员。
- 单一研究团队。
- 5 个并行研究项目起步，但数据模型不把项目数量写死。
- 私有部署。
- 管理员预先创建用户，不开放公众注册。
- 总负责人和研究成员两类组织角色。
- 项目主理人、协作者、方法挑战者、理论/复现挑战者等项目角色。
- 研究组合驾驶舱。
- 单项目研究驾驶舱。
- 非线性的研究网络、分支与回路。
- 多维科研状态，而不是单一“项目阶段”。
- 科学决策与重大科学决策双层审批。
- 科学决策锁。
- 科研事项、智能代理任务和智能代理运行的分离。
- DeepSeek Harness 作为智能代理执行平面。
- Codex、Claude Code 等通过 Harness 子代理机制接入。
- GitHub 作为代码与工程事实源。
- 共享科研资产及资产成熟度管理。
- 追加式科研事件账本。
- 可靠外部事件收件箱与事务发件箱。
- 自动化测试、代码审查和可审计部署流程。

### 2.2 第一版明确不做

- 公共注册。
- 多组织、多租户 SaaS。
- 计费与订阅。
- 社交社区功能。
- 通用插件市场。
- 自研大模型。
- 自建通用编码代理。
- 把 DeepSeek Harness 现有 Web 界面改造成科研工作台。
- 以 Kubernetes 为前提的复杂基础设施。
- 让工作台服务器直接开放任意代码执行。
- 让智能代理自动批准重大科学决策。
- 用工作台替代 GitHub 的代码版本控制、拉取请求和持续集成能力。
- 用 Harness Session 取代科研领域数据库。

## 3. 核心产品原则

### 3.1 人负责科学含义，智能代理负责受控执行

研究者决定为什么研究、研究什么、什么证据足以支持什么主张。智能代理负责把已明确的研究意图转成可执行、可检查、可重复的任务。

### 3.2 发现与批准分离

智能代理可以发现异常、提出模型修改、提出理论修订、建议新分析，但不能直接把这些建议变为正式科研状态。

### 3.3 科研不是线性流程

系统不能用单一阶段字段表达研究。研究必须支持回退、分叉、并行、重新开启、竞争解释和失败路线保留。

### 3.4 正式科研对象不可原地覆盖

正式研究问题、理论、研究设计、测量方案、数据版本、分析方案、研究结果和科研资产版本均采用版本化方式管理。修改意味着产生新版本，而不是覆盖旧版本。

### 3.5 论文不是结果存储位置

正式论文数字应能够追溯到研究结果记录、数据版本、代码提交和计算运行，而不是手工复制后失去来源。

### 3.6 GitHub 是工程事实源

代码发生了什么变化，以 GitHub 分支、提交、拉取请求、审查和持续集成记录为准。

### 3.7 DeepSeek Harness 是 AI 执行事实源

智能代理收到什么上下文、调用什么工具、执行什么操作、产生什么结果，以 Harness Session 和相关运行记录为准。

### 3.8 Research Workbench 是科研事实源

研究的正式问题、理论、设计、数据版本、正式结果、科学决策、审批、科研状态和资产成熟度，以 Research Workbench 为准。

## 5. DeepSeek Harness 复核结论及设计约束

基于当前 `bxbdndhfjfbdj2-creator/deepseek-harness` fork 的实际架构，第一版采用以下原则。

### 5.1 可以直接复用的 Harness 能力

- 追加式 Session 事件日志。
- Session 持久化和查询。
- Workspace 与 Session 关联。
- Tools 注册、限制、执行和审批策略。
- `user-approval` 一次性敏感操作审批。
- `user-questions` 在运行过程中暂停并向人提问。
- Permission Presets。
- Sandbox 的 `read-only`、`workspace-write`、`danger-full-access` 能力。
- Workflow 的并行、流水线、阶段化子代理编排。
- Subagent 统一提供者接口。
- Codex 真正子代理。
- Claude Code 真正子代理。
- SDK 的进程外 JSON-RPC 驱动。
- Jobs 的单次运行内部后台工作能力。
- Deliverables 与 Workspace Changes。
- Credentials 的凭据引用能力。

### 5.2 不能让 Harness 承担的职责

- 六人团队身份系统。
- 项目角色与组织授权。
- 科研正式状态。
- 重大科学决策审批。
- 跨项目共享资产治理。
- 可靠的长期任务队列。
- 外部 Webhook 的可靠去重、重试和持久化。
- 跨进程持久化科研工作流。
- 研究组合层面的风险和注意力管理。

### 5.3 第一版接入方式

Research Workbench 不直接修改 Harness Agent Loop，也不直接依赖 Harness Web UI。第一版优先通过 TypeScript SDK 驱动独立 Harness 运行时：

`Workbench Backend -> Reliable Queue -> Agent Worker -> Harness Adapter -> DeepSeekHarness SDK -> dsh SDK Profile`

Harness Web UI 保留为管理员和高级调试控制台。

## 6. 技术架构

### 6.1 第一版总体形态

第一版采用“模块化单体 + 独立 Agent Worker + 独立 Harness Runtime”的结构，而不是微服务化。

推荐运行单元：

- `web`：Research Workbench Web 应用。
- `worker`：可靠异步任务与 Agent Worker。
- `postgres`：科研业务事实源。
- `object-storage`：文件和大型产物。
- `deepseek-harness`：独立 AI 执行运行时。

### 6.2 推荐技术栈

- TypeScript。
- Node.js。
- pnpm。
- React + Next.js。
- PostgreSQL。
- Prisma 或 Drizzle 作为数据访问层，实施计划阶段择一。
- 第一版可靠任务队列优先基于 PostgreSQL，避免过早引入 Redis；如果实施验证表明不合适，再引入专用队列。
- S3 兼容对象存储。
- GitHub Actions。
- Docker Compose 起步。

### 6.3 环境

至少包含：

- 开发环境。
- 预发布环境。
- 正式环境。

正式环境不得由开发分支直接部署。

## 7. 六人组织与协作模型

### 7.1 组织角色

- 总负责人：1 人。
- 研究成员：5 人。

### 7.2 项目角色

每个研究项目至少支持：

- 研究主理人。
- 主要协作者。
- 方法挑战者。
- 理论/复现挑战者。
- 观察者。

一个人可以在不同项目承担不同角色。

### 7.3 推荐协作方式

每名研究成员主导一个研究，并深度参与另外两个研究。项目内形成“一个建设者 + 两个制度化挑战者”的三角结构，总负责人只在关键科学闸门和资源冲突时介入。

## 8. 信息架构与主导航

第一版主导航固定为：

1. 研究组合。
2. 研究项目。
3. 科学决策。
4. 智能工作。
5. 共享资产。
6. 团队。
7. 系统。

单个研究项目内固定为：

1. 总览。
2. 研究网络。
3. 证据与结果。
4. 科学决策。
5. 智能工作。
6. 项目资产。

## 9. 两类主要首页

### 9.1 总负责人：研究组合驾驶舱

首先展示：

- 五个项目的多维科研状态。
- 当前需要总负责人判断的科学决策。
- 主结果或正式数据发生重大变化的项目。
- 数据、识别、理论、复现、时间风险。
- 跨项目复用机会。
- 人员负载与临时协作需求。
- AI 执行异常。
- 投稿、返修、内部审验等关键时限。

首页的目标不是汇报全部活动，而是回答“整个团队当前有哪些事情真正需要人的注意力”。

### 9.2 研究成员：我的研究控制台

首先展示：

- 自己主导项目的最大科学不确定性。
- 等待本人判断的事项。
- 智能代理正在执行的任务。
- 交叉协作者提出的问题。
- 最近重要科研变化。
- 自己作为协作者参与的其他项目所需行动。

## 10. 研究项目模型

研究项目不是一个任务容器。项目包含研究网络、正式科研状态、科学决策、证据、智能工作和资产。

### 10.1 多维科研状态

每个项目至少跟踪以下维度：

- 研究问题。
- 理论。
- 测量。
- 研究设计。
- 数据。
- 主分析。
- 机制分析。
- 稳健性。
- 论文。
- 复现。
- 投稿。

第一版统一状态词汇：

- 未开始。
- 探索中。
- 候选。
- 待审查。
- 正式。
- 验证中。
- 稳定。
- 冻结。
- 重新开启。
- 受阻。
- 退休。

这些状态不是线性阶段，不要求按固定顺序迁移。

## 11. 研究网络、节点、分支与回路

### 11.1 研究节点 `ResearchNode`

第一版节点类型：

- 研究问题。
- 理论。
- 机制。
- 假设。
- 测量。
- 研究设计。
- 数据方案。
- 分析方案。
- 解释。
- 论文主张。

### 11.2 节点版本 `ResearchNodeRevision`

节点身份保持稳定，内容变化通过新版本记录。旧版本不得原地覆盖。

项目可以同时存在正式版本和候选版本。例如正式理论仍为 2.1，同时探索理论 3.0 候选版本。

### 11.3 研究关系 `ResearchEdge`

第一版关系类型：

- 来源于。
- 支持。
- 挑战。
- 检验。
- 依赖。
- 修订。
- 替代。
- 使用。
- 产生。
- 回到。

### 11.4 科研分支 `ResearchBranch`

科研分支表达一条科学探索路线，与 Git 分支严格区分。失败或被否定的科研分支不删除，而标记状态和终止原因，作为团队知识资产的一部分。

## 12. 科学决策与审批

### 12.1 科学决策 `ScientificDecision`

科学决策至少记录：

- 提议内容。
- 原因。
- 触发事件。
- 支撑证据。
- 影响范围。
- 提议者。
- 决策人。
- 决策结果。
- 完整时间信息。

智能代理可以创建决策提议，但不能创建已批准决策。

### 12.2 决策等级

一般科学决策：项目主理人可批准。

重大科学决策：项目主理人提议，总负责人批准。

重大科学变更包括：

- 核心研究问题。
- 正式理论框架。
- 主测量指标。
- 主样本。
- 主数据版本。
- 识别策略。
- 主模型。
- 探索结果升级为正式结果。
- 论文核心主张。

### 12.3 科学决策锁

系统必须保证以下不变量：

- AI 不能直接修改重大正式科研状态。
- 未完成规定的人类审批时，正式指针不得变化。
- 被拒绝的提议保留历史记录。
- 任何重大正式变更必须可以追溯到一个已批准科学决策。

## 13. 科研事项、智能代理任务与运行

### 13.1 科研事项 `ResearchTask`

表示科研上需要完成的工作，例如“解释数据 3.3 导致主效应下降的原因”。

### 13.2 智能代理任务 `AgentTask`

表示一个需要 AI 执行的受控任务。一个科研事项可以产生零个、一个或多个智能代理任务。

### 13.3 智能代理运行 `AgentRun`

表示一次实际执行尝试。一个 AgentTask 可以有多次 AgentRun，例如第一次失败、第二次成功。

运行状态：

- 已提议。
- 等待授权。
- 排队。
- 已派发。
- 执行中。
- 等待人工输入。
- 继续执行。
- 完成。
- 失败。
- 取消。
- 被替代。

### 13.4 上下文快照 `AgentContextSnapshot`

每次正式 AgentRun 必须冻结当时的执行上下文，至少记录：

- 研究问题版本。
- 理论版本。
- 研究设计版本。
- 数据版本。
- 相关资产版本。
- Git 基础提交。
- 智能代理技能版本。
- Harness 版本。
- Harness Profile。
- 模型路由。
- 权限策略。

禁止依赖模型隐藏推理作为审计依据。审计对象是输入上下文、可见消息、工具调用、工具结果、文件变化、工程变化和正式输出。

## 14. 智能代理权限模型

AI 行为分四级：

1. 观察：只读、总结、分析。
2. 建议：产生候选方案，不修改正式状态。
3. 受控执行：在已授权范围内执行数据、代码或分析任务。
4. 科学变更：禁止自动执行，必须转换为人类科学决策。

用户不需要主动选择“用哪个 AI”。Workbench 根据任务类型决定 Harness 配置和子代理提供者；高级用户可查看具体模型、子代理、工具和 Session 细节。

## 15. Harness 执行协议

Workbench 通过 `HarnessAdapter` 把科研语义转换为 Harness 执行请求。

### 15.1 典型请求包含

- 项目标识。
- 科研事项标识。
- AgentTask 标识。
- 上下文快照。
- 工作目录。
- 允许读取的资产。
- 允许使用的工具。
- 允许使用的子代理。
- 沙箱策略。
- 最大执行权限。
- 是否需要人类问答。
- 预期结构化输出。

### 15.2 典型返回包含

- Harness Session 标识。
- 状态。
- 可见消息摘要。
- 关键工具调用事实。
- 产生的结果。
- 产生的文件或交付物。
- GitHub 关联信息。
- 科学变更提议。
- 错误和停止原因。

Workbench 不能把 Harness 最终文本直接等同于正式科研结论。

## 16. Codex 与 Claude Code

第一版不由 Workbench 自己实现 Codex / Claude Code 协议，而复用 Harness 的 `subagent-codex` 和 `subagent-claude-code`。

代码类任务的正式工程证据必须落到 GitHub。Harness 子代理的最终文本只能作为执行反馈，不能替代 Branch、Commit、Pull Request 和 CI 记录。

典型链路：

`ResearchTask -> AgentTask -> Harness Session -> Codex/Claude Code -> GitHub Branch -> Commit -> Pull Request -> CI -> Review -> Workbench Result`

## 17. GitHub 集成

### 17.1 GitHub 引用 `GitHubReference`

Workbench 不复制 GitHub 全量数据，只记录科研对象与 GitHub 工程对象的关联。

第一版类型：

- Issue。
- Branch。
- Commit。
- Pull Request。
- Review。
- Workflow Run。

### 17.2 工程工作流

重要代码变更采用：

- 功能分支。
- 自动测试。
- 拉取请求。
- 代码审查。
- CI。
- 人工合并。

默认禁止智能代理直接修改 `main`。

### 17.3 GitHub Webhook

GitHub 外部事件必须先进入 Workbench 的可靠事件收件箱，再去重和异步处理。不得直接依赖 Harness Webhook 的 fire-and-forget 语义来更新科研正式状态。

## 18. 结果与证据模型

### 18.1 研究结果 `ResearchResult`

一次正式计算产生一个不可变结果。重新运行生成新结果，不覆盖旧结果。

每个结果至少关联：

- 数据版本。
- 分析方案版本。
- 代码提交。
- AgentRun 或人工运行记录。
- Harness Session（若适用）。
- 执行时间。
- 输出文件。

### 18.2 结果替代关系

新结果可以标记 `supersedes` 旧结果，但旧结果仍保留。

### 18.3 论文数字追溯

正式论文中的核心数字应能够映射到 ResearchResult，而不是仅存在于 Word/LaTeX 文本中。

## 19. 科研资产模型

### 19.1 资产 `ResearchAsset`

第一版资产类型：

- 数据资产。
- 数据处理资产。
- 指标资产。
- 方法资产。
- 模型资产。
- 文献资产。
- 文档资产。
- 智能代理资产。

### 19.2 资产版本 `ResearchAssetVersion`

资产版本不可原地覆盖。

### 19.3 成熟度

- 实验性。
- 项目级。
- 团队级。
- 发布级。

### 19.4 资产使用 `AssetUsage`

必须记录哪些项目使用了哪个具体资产版本，从而支持影响分析。

### 19.5 资产升级

从项目级升级到团队级必须经过人工确认。系统可以自动发现重复能力和候选复用机会，但不能自动宣布某个资产为团队正式资产。

## 20. 团队注意力与通知

主动打扰用户的事件第一版限制为四类：

- 科学决策。
- 研究异常。
- 协作请求。
- 时限事件。

普通 Agent 运行完成、常规后台任务进展等默认进入工作台而非单独推送。

研究组合会议前，系统生成面向讨论的简报，只突出需要人类判断的问题，而不是逐项目流水账。

## 21. 科研事件账本

### 21.1 `ResearchEvent`

所有重要科研变化产生追加式事件。事件一旦写入不得修改或删除。

第一版至少包含：

- `PROJECT_CREATED`
- `RESEARCH_NODE_CREATED`
- `NODE_REVISION_CREATED`
- `NODE_REVISION_PROPOSED`
- `SCIENTIFIC_DECISION_CREATED`
- `SCIENTIFIC_DECISION_APPROVED`
- `SCIENTIFIC_DECISION_REJECTED`
- `OFFICIAL_REVISION_CHANGED`
- `RESEARCH_STATE_CHANGED`
- `RESEARCH_BRANCH_CREATED`
- `RESEARCH_BRANCH_CLOSED`
- `AGENT_TASK_CREATED`
- `AGENT_RUN_STARTED`
- `AGENT_RUN_WAITING_HUMAN`
- `AGENT_RUN_COMPLETED`
- `AGENT_RUN_FAILED`
- `RESULT_CREATED`
- `ASSET_VERSION_CREATED`
- `ASSET_PROMOTED`
- `GITHUB_REFERENCE_LINKED`

Workbench 不采用纯事件溯源。当前状态仍保存在关系表中；ResearchEvent 用于解释“为什么变成现在这样”。

## 22. 可靠异步架构

### 22.1 事务发件箱 `OutboxEvent`

凡是数据库事务提交后需要触发的外部副作用，例如：

- 派发 AgentTask。
- 通知用户。
- 调用 GitHub。
- 更新搜索索引。

必须通过事务发件箱触发，而不是在业务事务中直接调用外部系统。

### 22.2 外部事件收件箱 `IntegrationInbox`

GitHub Webhook 等外部事件必须：

1. 先持久化。
2. 以外部事件唯一标识去重。
3. 异步处理。
4. 记录成功或失败。
5. 支持安全重试。

同一事件重复到达不得重复改变正式科研状态。

## 23. 身份、认证与授权

第一版不使用 Harness 匿名 identity 作为团队身份。

Workbench 独立管理六个内部用户账户。

身份要求：

- 管理员预创建用户。
- 不开放注册。
- 密码或外部身份提供者的具体选择在实施计划阶段确定，但不得让 Harness Session 代替用户身份。
- 所有关键操作必须记录操作者。
- 智能代理作为系统执行主体拥有独立 actor 类型，不伪装成人类用户。

授权采用“组织角色 + 项目角色 + 操作权限”的组合。

## 24. 凭据与秘密管理

- 数据库密码、模型密钥、GitHub 凭据等不得进入科研事件、AgentContextSnapshot 或普通日志。
- Workbench 数据库只保存凭据引用或密钥管理系统标识。
- Harness 可使用自身 Credentials seam，但 Workbench 仍负责谁可以要求使用某个凭据。
- Codex/Claude Code 子代理的环境变量必须使用明确白名单，不继承无关秘密。

## 25. 沙箱与代码执行安全

第一版坚持混合型模式：Workbench 本身不开放任意代码执行。

代码执行由 Harness 和外部编码代理承担。

默认原则：

- 探索性读取：`read-only` 优先。
- 需要修改项目文件：`workspace-write`。
- `danger-full-access` 不作为默认配置，并要求显式管理员策略。
- 如果 Harness 无法落实要求的沙箱，执行失败关闭，不降级为无沙箱运行。
- 高风险外部副作用必须经过 Harness 一次性工具审批和/或 Workbench 业务审批。

## 26. 数据库设计原则

采用 PostgreSQL 的“当前状态 + 不可变版本 + 追加事件”模式。

### 26.1 当前状态表

用于快速回答：

- 项目当前正式研究问题是什么。
- 当前正式数据版本是什么。
- 当前主模型是什么。
- 当前各研究维度状态是什么。

### 26.2 不可变版本表

用于保存：

- 节点版本。
- 数据版本元信息。
- 分析方案版本。
- 资产版本。
- 结果。

### 26.3 追加式事件表

用于保存重要历史变化与审计事实。

## 28. 关键系统不变量

以下规则必须进入自动化测试：

1. 智能代理不能直接修改正式科研状态。
2. 重大科学变更必须有人类批准。
3. 正式版本不能原地覆盖。
4. 已记录研究结果不能修改。
5. 已发生科学决策不能删除。
6. AgentRun 必须关联上下文快照。
7. 正式 Harness 执行必须关联 AgentRun。
8. 正式代码结果必须关联 Git 提交。
9. 凭据不得进入科研日志和 AI 审计记录。
10. ResearchEvent 只能追加。
11. 外部事件必须幂等处理。
12. 正式资产必须定位到具体版本。
13. 失败的科研分支不得因“未采用”而静默消失。
14. AI 产生的科学变更只能先成为提议。
15. 未满足审批链时，正式指针不得发生变化。

## 29. 错误处理原则

- 权限不足：失败关闭，不自动提升权限。
- Harness 不可用：AgentTask 保留并进入可重试状态，不改变正式科研状态。
- GitHub 不可用：工程动作保持待处理，不能伪造完成。
- Webhook 重复：幂等去重。
- Agent 运行失败：保存失败 Run，可创建新 Run 重试。
- AI 输出格式错误：运行失败或进入人工检查，不尝试静默修补为正式事实。
- 审批请求无人处理：保持等待，不采用默认批准。
- 沙箱不可用：执行失败，不自动改为完全访问。
- 数据库事务失败：不产生部分正式状态变化。

## 30. 可观测性

第一版至少记录：

- Web 请求和后端错误。
- 任务队列延迟和失败。
- AgentTask 与 AgentRun 状态。
- Harness 子进程启动、退出和错误。
- GitHub 集成失败。
- Webhook 去重和重试。
- 科学决策等待时长。
- 不记录模型隐藏推理。
- 不记录原始密钥。

## 31. 第一版验收场景

第一版必须以端到端场景验收，而不是只检查页面存在。

### 31.1 核心科研闭环

1. 创建研究甲。
2. 指定研究主理人和两名协作者。
3. 创建研究问题节点并设置正式版本。
4. 创建理论和研究设计节点。
5. 登记数据资产版本。
6. 创建一个科研事项。
7. 从科研事项生成 AgentTask。
8. Agent Worker 调用 Harness。
9. Harness 运行数据诊断。
10. 创建 ResearchResult。
11. 检测到异常并创建研究异常事件。
12. AI 创建一个科学变更提议。
13. 项目主理人审查。
14. 因属于重大变化，转总负责人批准。
15. 批准后正式指针更新。
16. 原版本仍然可见。
17. 产生 ResearchEvent。
18. 若涉及代码，关联 GitHub Branch/Commit/PR。
19. 若形成通用工具，创建共享资产升级候选。
20. 人工批准后升级为团队级资产。

### 31.2 失败与重试

- AgentRun #1 失败。
- AgentTask 不丢失。
- 创建 AgentRun #2。
- Run #1 保留。
- Run #2 成功后形成结果。

### 31.3 科学决策锁

- AI 提议修改主模型。
- AI 无法修改 official model。
- 主理人批准后，如果属于重大决策，official model 仍不变化。
- 总负责人批准后创建新模型版本并更新正式指针。
- 旧模型版本保留。

### 31.4 GitHub 真实性

- 编码代理声称修改完成但没有 Git Commit：不能标记正式工程工作完成。
- 有 Commit 但 CI 失败：不能标记工程验收通过。
- PR 合并并 CI 通过后，Workbench 才能把对应工程工作标记为已验证。

### 31.5 外部事件幂等

- 同一 GitHub Webhook 连续投递三次。
- IntegrationInbox 保存并识别重复。
- 只产生一次业务状态变化。

## 32. 质量闸门

产品开发本身必须遵循：

- 规格先行。
- 实施计划先行。
- 测试驱动开发。
- 每个重要功能完成后代码审查。
- 合并 `main` 前自动测试。
- 预发布环境人工验收。
- 正式环境部署后进行烟雾测试。

科研业务中的关键质量闸门第一版包括：

- 研究问题成立。
- 研究设计可信。
- 数据可信。
- 证据可信。
- 投稿准备。
- 资产升级。

## 33. 部署与版本策略

推荐代码仓库：

- `research-workbench`：独立科研工作台。
- `deepseek-harness`：用户 fork，尽量跟踪上游，只保留必要补丁。

`research-workbench` 对 Harness 通过 Adapter/SDK 依赖，不把科研业务代码直接写入 Harness 核心。

部署采用：

`GitHub -> CI -> 构建镜像 -> 预发布 -> 人工验收 -> 正式环境`

## 34. 与 Harness 的升级隔离

DeepSeek Harness 当前仍处于快速迭代和预稳定 API 阶段，因此 Workbench 不应让业务代码大量直接依赖 Harness 内部包。

所有 Harness 交互必须集中到 `HarnessAdapter` 及少量边界类型中。

Harness 升级时优先通过适配层消化变化，不要求科研领域模块跟随修改。

## 35. 第一版成功标准

第一版被认为成功，需要同时满足：

1. 六名成员可以登录并按各自角色看到对应科研注意力视图。
2. 五个项目能够并行存在且独立跟踪多维科研状态。
3. 研究路线可以分叉、回退、重新开启并保留失败历史。
4. AI 可以被派发受控任务并通过 Harness 执行。
5. Codex/Claude Code 至少一种真实子代理链路能够在测试环境完成 GitHub 工程任务。
6. 重大科学变化无法绕过人工审批。
7. 研究结果能够追溯到数据版本、代码提交和运行记录。
8. 跨项目资产可以被发现、升级、版本化和追踪使用关系。
9. GitHub 与 Harness 任一暂时不可用时，不会造成正式科研状态静默损坏。
10. 核心端到端验收场景通过自动测试和人工验收。

## 36. 后续版本方向（不属于第一版承诺）

可能的后续演进包括：

- 从固定六人扩展到可配置团队规模。
- 多团队/多组织。
- 更强的知识图谱查询。
- 远程隔离计算环境、容器或微型虚拟机。
- 专门的计算实验资源调度。
- 更丰富的论文和文献工作流。
- 外部数据仓库连接器。
- 更复杂的 Agent Team 策略。
- 自动生成科研组合月报和管理报告。
- 资产依赖图与变更影响自动传播。
- 更精细的科研透明性与开放科学发布功能。

这些方向不得反向扩大第一版范围。

## 37. 规格自检结论

本规格当前没有未决占位符；第一版产品边界、总体架构、Harness 分工、角色模型、科研状态机制、研究网络、科学决策、AI 权限、GitHub 集成、资产治理、可靠异步模式和核心验收条件均已给出明确默认方案。

实施阶段仍需做技术选型细化，例如 Prisma 与 Drizzle 二选一、具体认证实现和 PostgreSQL 队列实现，但这些属于实施方案选择，不改变本文定义的产品和架构契约。
