# 组织制度语言 0.2 设计规格

## 一、阶段目标

0.2 的目标不是继续增加固定业务按钮，而是让“组织如何被定义、允许发生什么动作、界面提供什么操作”从 JavaScript 常量中脱离出来，成为可版本化、可编译、可兼容检查、可在线生效的中文制度源码。

核心原则：

> 运行时内核长期稳定；制度可以演化；组织状态持续运行。

0.2 必须在不重新部署网页、不重置当前组织世界、不丢失事件历史的前提下，让一份新的制度源码经过编译和兼容性检查后在线生效。

## 二、成功标准

第一版 0.2 被认为成立，至少满足：

1. 当前 `ORGANIZATION_MODEL` 不再是运行时唯一真相；组织模型由中文制度源码编译得到。
2. 制度源码至少可以定义：存在类型、状态槽、关系类型、动作、动作输入、动作前置条件、动作效果。
3. 编译器确定性运行，不调用人工智能。
4. 动作定义编译后可以直接驱动组织运行时，不再要求 `app.js` 为每个动作写专用分支。
5. 动作输入定义可以驱动通用网页表单：文本输入生成文本框，实体类型输入生成当前世界实体选择器。
6. 新制度必须先完成语法检查、语义检查和当前世界兼容性检查，才能生效。
7. 不会让当前世界事实失效的制度变更可以在线生效，不重新部署服务。
8. 会让当前世界实体、状态或关系失效的制度变更必须被拒绝，并返回具体冲突事实。
9. 制度生效本身进入事件历史；普通运行事件必须记录它执行时所使用的制度版本。
10. “运行时格式版本”和“制度版本”必须完全分离。
11. 现有 0.1 浏览器快照必须可以安全迁移到 0.2 格式；不得要求用户为了升级主动清空当前组织状态。
12. 现有人员、部门、项目、关系、事件事务和浏览器持久化能力继续工作。
13. 第一阶段仍不实现服务器数据库、多人协作、权限认证、自动数据迁移脚本、自由自然语言理解和人工智能生成制度。

## 三、总体架构

```text
中文制度源码
    │
    ▼
制度解析器
    │
    ▼
制度语法树
    │
    ▼
制度编译器
    │
    ▼
编译后制度模型
    │
    ├───────────────┐
    ▼               ▼
兼容性检查器      动作解释器
    │               │
    ▼               ▼
制度激活器        通用事件事务
    │               │
    └───────┬───────┘
            ▼
       当前组织世界
            │
            ▼
          动态 GUI
```

运行时内核继续只认识通用世界操作：

```text
创建存在
设置状态
建立关系
取消关系
```

“入职”“调岗”“创建委员会”“加入项目”等仍然不进入核心内核，而由制度中的动作编译成上述通用操作。

## 四、制度源码 0.2

### 1. 设计原则

第一版采用受约束、可确定解析的中文声明式语法。

- 不使用自由自然语言。
- 结构词使用中文。
- 通过换行和显式 `结束` 划分块，不依赖缩进语义。
- 名称第一版不得包含空格。
- 结构词之间要求空白分隔。
- `?名称` 表示动作中的绑定名；它不是用户可见数据，而是制度内部引用。
- 同一制度版本内，存在类型、关系、动作名称必须唯一。

### 2. 制度头

```text
制度 星河组织制度
版本 组织制度-2
```

`制度` 名称用于识别制度族；`版本` 是业务制度版本标识。

同一运行时历史中不得激活两个相同的制度版本标识。

### 3. 存在类型

```text
存在类型 成员
状态 任职状态 初始 在职 可为 在职 离职
结束

存在类型 部门
状态 生命周期状态 初始 运行中 可为 运行中 已结束
结束
```

一个存在类型可以声明零个或多个状态槽。

`初始` 只表示以后通过制度动作创建新存在时使用的默认值；它不意味着制度升级时自动回填旧实例。

0.2 不引入“必填状态槽”的语义，因此旧实例缺少后来新增的状态槽仍然是合法世界。

### 4. 关系类型

```text
关系 属于
从 成员
到 部门
结束

关系 负责人
从 部门 项目组
到 成员
结束
```

`从` 和 `到` 可以各接受一个或多个存在类型。

关系仍然是有方向的。

### 5. 动作

动作定义允许用户发起一个领域级操作，但动作最终必须编译成通用世界操作。

```text
动作 创建部门
输入 名称 文本
则 创建 ?部门 是 部门 名称 ?名称
结束
```

实体类型输入：

```text
动作 人员调岗
输入 成员 成员
输入 原部门 部门
输入 新部门 部门
要求 关系 ?成员 的 属于 为 ?原部门
则 取消关系 ?成员 的 属于 为 ?原部门
并 建立关系 ?成员 的 属于 为 ?新部门
结束
```

第一版输入类型只支持：

```text
文本
已定义的存在类型
```

第一版前置条件只支持：

```text
要求 关系 ?主体 的 <关系> 为 ?客体
要求 状态 ?存在 的 <状态槽> 为 <状态值或绑定>
```

多个 `要求` 之间是“并且”关系。

第一版动作效果只支持：

```text
创建 ?绑定 是 <存在类型> 名称 ?名称输入
设置状态 ?存在 的 <状态槽> 为 <值>
建立关系 ?主体 的 <关系> 为 ?客体
取消关系 ?主体 的 <关系> 为 ?客体
```

`并` 与 `则` 后的效果按源码顺序执行，但整个动作仍作为一次原子事务提交。

### 6. 创建存在时的初始状态

当动作执行：

```text
创建 ?部门 是 部门 名称 ?名称
```

动作解释器必须从当前编译制度读取 `部门` 的初始状态声明，并把它们一起物化成明确的“创建存在”操作。

因此核心运行时无需理解“初始状态”。

## 五、编译后制度模型

中文源码不能直接被世界运行时解释。编译器输出稳定中间表示，至少包含：

```text
制度名称
制度版本
存在类型定义
状态定义
关系定义
动作定义
```

概念结构等价于：

```text
制度模型
├── 元数据
├── 存在类型
│   └── 状态槽 / 可选值 / 初始值
├── 关系类型
│   └── 主体允许类型 / 客体允许类型
└── 动作
    ├── 输入
    ├── 前置条件
    └── 效果模板
```

运行时只依赖这个编译结果，不依赖源码文本格式。

因此以后语法扩展时，只要编译结果兼容，世界运行时无需修改。

## 六、动作物化与运行

动作执行分两步。

### 1. 物化

例如：

```text
动作 创建部门
输入 名称 文本
则 创建 ?部门 是 部门 名称 ?名称
结束
```

用户输入：

```text
名称 = 人工智能部
```

动作解释器先：

1. 校验输入；
2. 为 `?部门` 生成实体标识；
3. 读取 `部门` 初始状态；
4. 得到普通通用事件操作。

结果等价于：

```text
创建存在
    标识 = 自动生成
    名称 = 人工智能部
    类型 = 部门
    生命周期状态 = 运行中
```

### 2. 事务执行

物化后的操作继续交给现有原子事件事务执行器。

因此 0.2 不重新实现事务、回滚和关系校验。

前置条件不满足时，动作产生失败事件，世界保持不变，失败原因进入审计历史。

## 七、GUI 由制度动作驱动

0.2 必须删除 `app.js` 中动作名称到表单字段的硬编码映射。

操作面板读取当前制度的动作列表。

例如：

```text
动作 人员调岗
输入 成员 成员
输入 原部门 部门
输入 新部门 部门
```

自动生成：

```text
人员调岗

成员
[ 当前成员 ▼ ]

原部门
[ 当前部门 ▼ ]

新部门
[ 当前部门 ▼ ]

[执行事件]
```

规则：

- `文本` → 文本输入框；
- `成员` → 当前世界中所有“成员”实体选择器；
- `部门` → 当前世界中所有“部门”实体选择器；
- 其他后来新增存在类型同理；
- 已结束或离职实体是否出现在候选项中，0.2 由通用候选过滤规则处理，不由每个动作单独写代码。

第一版候选过滤规则：

- `任职状态 = 离职` 的成员默认不进入动作选择器；
- `生命周期状态 = 已结束` 的非成员默认不进入动作选择器；
- 查看历史和详情时仍然保留这些实体。

## 八、动态存在类型的展示

0.2 允许新增如“委员会”的存在类型，因此网页不能只假定世界永远只有成员、部门、项目组。

保留现有“人员”“部门”“项目”专门视图，同时增加一个由制度模型驱动的“其他组织对象”区域：

- 当前制度中不属于成员、部门、项目组的存在类型会自动出现；
- 每个类型自动有列表和基础详情；
- 基础详情显示状态、作为主体的关系、作为客体的关系和相关事件；
- 第一版不自动生成专门视觉布局。

因此新增：

```text
存在类型 委员会
```

生效后无需改前端代码，即可看到“委员会”对象并通过动作创建实例。

## 九、制度编译与检查流程

制度编辑不会直接修改当前制度。

流程固定为：

```text
编辑候选源码
↓
解析
↓
语法检查
↓
语义检查
↓
编译候选制度
↓
用候选制度验证当前世界
↓
生成兼容性报告
↓
允许生效 / 拒绝生效
```

### 1. 语义检查至少包括

- 制度名和版本存在；
- 名称唯一；
- 状态槽引用的存在类型已声明；
- 初始状态属于允许值；
- 关系主体/客体类型已声明；
- 动作输入类型有效；
- 动作绑定名不重复；
- 动作条件引用有效；
- 动作效果引用有效；
- 设置状态的槽和值合法；
- 建立/取消关系的端点类型在静态上可满足关系定义。

### 2. 编译错误

错误至少包含：

```text
错误类型
行号
原始行
中文说明
```

一个候选制度编译失败时，当前运行制度完全不受影响。

## 十、制度兼容性检查

0.2 不通过手写“允许新增、禁止删除”规则判断兼容，而采用更基础的原则：

> 当前世界中的每一个事实，在候选制度下仍然必须合法。

检查器必须用候选制度重新验证：

1. 每个当前实体的类型仍然存在；
2. 每个当前实体已经拥有的状态槽仍然存在；
3. 每个当前状态值仍然被允许；
4. 每条当前关系类型仍然存在；
5. 每条当前关系的主体类型与客体类型仍符合候选制度。

全部通过则该候选制度对“当前世界”兼容。

### 兼容示例

新增：

```text
存在类型 委员会
关系 参加
从 成员
到 委员会
结束
```

不会使当前事实非法，因此兼容。

改变动作实现、增加动作、删除动作也不会直接使已有世界事实非法，因此第一版允许激活；历史制度版本保证可审计。

### 不兼容示例

当前存在：

```text
火星计划 是 项目组
```

候选制度删除 `项目组`，则拒绝激活。

当前存在：

```text
张三 的 任职状态 = 在职
```

候选制度把允许值改成：

```text
正式 临时
```

则拒绝激活。

当前存在：

```text
张三 —参与→ 火星计划
```

候选制度删除 `参与` 或修改其端点使该关系不合法，则拒绝激活。

兼容性错误必须尽可能返回具体冲突实体、状态或关系，而不是只返回“版本不兼容”。

## 十一、0.2 不自动做数据迁移

如果一个制度变化会让当前世界非法，0.2 只拒绝生效。

不自动：

- 删除实体；
- 改写关系；
- 重命名类型；
- 批量替换状态值；
- 自动迁移历史数据。

以后可以增加显式“世界迁移程序”，但它必须是另一个可审计事务，不属于 0.2。

因此 0.2 的原则是：

> 先证明制度可以安全演化，再处理复杂数据迁移。

## 十二、制度激活

候选制度通过兼容性检查后，可以执行“使其生效”。

激活必须是一次原子持久化：

```text
旧当前制度
+ 候选制度
+ 当前世界
+ 现有事件历史
↓
一次提交
↓
新当前制度
+ 更新后的制度历史
+ 原世界
+ 新增制度生效事件
```

任何存储失败都必须保持旧制度继续运行。

制度激活事件至少记录：

```text
事件类型 = 制度生效
原制度版本
新制度版本
发生时间
状态 = 成功
```

普通运行事件记录中增加：

```text
制度版本
```

用来回答“这个事件发生时适用哪一版制度”。

## 十三、运行时格式版本与制度版本分离

0.1 把模型版本直接用于整个浏览器快照兼容判断，这在制度可演化以后不再成立。

0.2 快照顶层改为：

```text
运行时格式版本
当前制度
制度历史
当前世界
事件历史
```

逻辑结构：

```text
运行时格式版本：组织运行时-2

当前制度：
    制度名称
    制度版本
    中文源码
    编译结果
    生效时间

制度历史：
    [...]

当前世界：
    {...}

事件历史：
    [...]
```

`运行时格式版本` 只在软件持久化结构本身变化时修改。

`制度版本` 可以在组织正常运行期间频繁变化。

世界不再因为制度版本变化而被存储层拒绝读取。

## 十四、从 0.1 快照安全迁移到 0.2

现有网页已经使用：

```text
organization-runtime-v0.1
```

作为浏览器存储键。

0.2 第一次启动时必须：

1. 优先检查 0.2 新快照；
2. 若不存在，再检查 0.1 快照；
3. 验证 0.1 快照结构；
4. 把原 `ORGANIZATION_MODEL` 对应的制度内容作为“初始制度”写入 0.2；
5. 原 `world` 原样迁移；
6. 原 `events` 原样迁移，并把其制度版本标记为 `组织制度-1` 或明确的“迁移前制度”；
7. 一次性写入 0.2 新键；
8. 新键写入成功前绝不删除 0.1 数据；
9. 第一版即使迁移成功，也保留 0.1 键作为可恢复副本，不主动删除。

如果 0.1 数据损坏，显示明确错误并保留原始数据，不自动重置。

## 十五、初始制度

为了保持当前 0.1 行为，项目内提供一份初始中文制度源码，编译后必须表达当前稳定模型，并覆盖现有主要动作：

- 成员入职；
- 创建部门；
- 成员加入部门；
- 成员移出部门；
- 人员调岗；
- 创建项目；
- 成员加入项目；
- 成员退出项目；
- 更换负责人；
- 成员离职；
- 结束部门或项目。

现有 `organization-actions.js` 的语义必须由这份初始制度的动作定义取代。

完成迁移后，不允许网页继续依赖硬编码动作函数作为主路径。

## 十六、制度页面

“制度”页升级为真正的制度管理入口。

### 当前制度

显示：

- 制度名称；
- 制度版本；
- 生效时间；
- 当前源码；
- 编译后的存在类型、关系、动作摘要。

### 编辑候选版本

提供源码编辑区和：

```text
检查制度
```

按钮。

检查结果显示：

- 语法/语义错误；
- 编译摘要；
- 与当前制度的变化摘要；
- 与当前世界的兼容性；
- 具体阻塞原因。

只有检查通过且兼容时才显示：

```text
使其生效
```

### 制度历史

按时间显示已激活的制度版本，可以查看历史源码和编译摘要。

第一版不提供直接回滚按钮；旧制度重新生效也必须作为新的候选版本通过兼容性检查，避免把“回滚”误认为无风险操作。

## 十七、委员会验收场景

0.2 的核心验收必须从一个已经运行过的组织世界开始。

### 当前状态

已有：

```text
成员
部门
项目组
若干关系
若干历史事件
```

### 新制度候选

在制度中增加：

```text
存在类型 委员会
状态 生命周期状态 初始 运行中 可为 运行中 已结束
结束

关系 参加
从 成员
到 委员会
结束

动作 创建委员会
输入 名称 文本
则 创建 ?委员会 是 委员会 名称 ?名称
结束

动作 加入委员会
输入 成员 成员
输入 委员会 委员会
则 建立关系 ?成员 的 参加 为 ?委员会
结束
```

### 验收步骤

1. 当前组织已有人员、部门、项目和事件历史；
2. 打开制度页创建新候选版本；
3. 编译通过；
4. 兼容性检查通过；
5. 在线激活，不重新部署网页；
6. 原有组织世界和事件历史完全保留；
7. 操作面板自动出现“创建委员会”“加入委员会”；
8. GUI 自动识别“委员会”为新增组织对象类型；
9. 创建“架构委员会”；
10. 将现有成员加入该委员会；
11. 页面显示委员会实例和“参加”关系；
12. 普通事件记录新制度版本；
13. 制度历史保留旧制度和新制度。

随后建立一个破坏性候选版本：删除 `项目组` 类型，而当前仍有项目实例。

系统必须：

- 编译候选制度本身可以成功；
- 兼容性检查失败；
- 明确列出仍存在的项目实例；
- 不显示可激活状态；
- 当前制度、当前世界和历史完全不改变。

## 十八、错误与安全边界

0.2 必须显式处理：

- 制度语法错误；
- 未声明类型引用；
- 重复名称；
- 非法状态定义；
- 非法关系端点；
- 动作引用不存在绑定；
- 动作输入缺失；
- 动作输入实体类型不匹配；
- 前置条件不满足；
- 候选制度与当前世界不兼容；
- 制度版本重复；
- 存储迁移失败；
- 激活持久化失败。

任何一种失败都不得把系统留下半更新状态。

所有用户输入名称和制度源码在 GUI 展示时继续进行 HTML 转义。

## 十九、明确不做

0.2 暂不实现：

- 自由自然语言制度；
- AI 把自然语言自动转换成制度；
- 条件中的或/非/量词；
- 递归推理；
- 时间条件；
- 权限认证；
- 多人并发制度编辑；
- 自动数据迁移；
- 制度分支合并；
- 制度回滚快捷按钮；
- 服务器数据库；
- 实时多人协作；
- AI 动态生成 GUI。

## 二十、阶段完成后的架构含义

0.2 完成后，系统将从：

```text
固定 JavaScript 组织模型
+ 动态组织状态
```

升级为：

```text
稳定世界运行时
+
可编译、可版本化、可热更新的组织制度
+
持续演化的当前组织世界
+
由制度与世界共同驱动的网页 GUI
```

最终原则：

> 组织结构变化不需要编译。
>
> 制度变化需要编译，但不需要重新部署运行时。
>
> 任何制度升级都不能破坏已经存在的组织事实。
